## 2. Объём проекта

1. **Функциональный** – полностью работоспособная вики с управлением пользователями, ролями, правами, редактором, версионированием, теговым поиском, импортом PDF‑файлов из Confluence, админ‑панелью, аудит‑логом и возможностью потоковой передачи (streaming) больших медиа‑файлов.
2. **Модуль компетенций** – единый каталог компетенций компании; карты компетенций подразделений; подготовка и модерация вопросов, полученных от внешней нейросети; составление тестов; назначение тестов и собеседований; однократное прохождение назначенного теста; тесты с произвольно создаваемыми блоками компетенций; самостоятельное тестирование по дополнительным компетенциям; оценки по каждой компетенции в шкале 0–3; личный кабинет и руководительская сводка.
3. **Нефункциональный** – базовая OWASP‑защита, шифрование медиа‑данных (at‑rest), поддержка до 200 RQ/сек, тестовое покрытие (unit + integration + e2e), развёртывание через Apache + mod_wsgi, плановая миграция к TLS.

### 3.8. Модуль тестирования и оценки компетенций сотрудников (новый функциональный блок)

#### 3.8.1. Назначение и общая логика

Модуль предназначен для определения фактических знаний и навыков сотрудников, включая компетенции, применимые в нескольких смежных подразделениях. Результаты позволяют руководителям выявлять потенциальных исполнителей задач в других отделах; **автоматическое распределение людей по задачам, выдача поручений или перевод сотрудников в первую версию не входят**.

Переход: **база знаний → меню профиля пользователя → личный кабинет → «Мои компетенции»**. По этому маршруту открывается одна область интерфейса с функциями, зависящими от полномочий пользователя. Пользователь всегда видит собственные компетенции и назначения. Сервер проверяет права независимо от отображения кнопок и разделов в UI.

#### 3.8.2. Роли и полномочия

| Участник | Доступные действия | Ограничения |
|---|---|---|
| **Сотрудник** | Просмотр своих компетенций, уровней 0–3 и истории оценок; просмотр назначенных проверок и сроков; прохождение назначенного теста; самостоятельный выбор дополнительных компетенций из каталога и немедленный запуск доступного опубликованного теста; просмотр сведений о назначенном собеседовании | Не составляет и не назначает проверки; не изменяет результаты и ключи правильных ответов |
| **Руководитель подразделения** | Просмотр сводки по своим подчинённым; просмотр оценок по компетенциям и результатов проверок; выбор сотрудников и назначение подготовленных тестов/собеседований с датой исполнения; определение потребности отдела в компетенциях; **утверждение карты своего подразделения** | Не получает автоматически доступ к сотрудникам чужого отдела и чужим результатам |
| **Ответственный за КК (карту компетенций)** | Работа с картой своего подразделения; выбор компетенций из общего каталога; получение и проверка импортированных AI-вопросов; отклонение/принятие вопросов; составление и публикация тестов по компетенциям | Не назначает тесты сотрудникам в базовом процессе; не подменяет итоговые оценки |
| **Собеседующий** | Просмотр назначенного ему собеседования, его списка компетенций; фиксация результатов и комментариев по каждой компетенции | Доступ только к тем собеседованиям, где назначен собеседующим |
| **Администратор системы** | Ведение общего справочника компетенций, управление назначениями функциональных ролей и аудитом | Действия протоколируются; обычные ограничения видимости данных требуют отдельной настройки административного доступа |

**Разделение полномочий.** Роль «Ответственный за КК» и полномочие «Собеседующий» вводятся **в контексте модуля**; они могут быть назначены сотруднику дополнительно к базовой роли из п. 3.1.2. Наличие роли «Руководитель» в вики само по себе не должно автоматически открывать данные всех подразделений. Для MVP действует **один руководитель на подразделение**: таблица `departments` ссылается на руководителя (`manager_id → users.id`) либо используется эквивалентная однозначная связь. Подчинённые определяются по `users.department_id`; руководитель видит сотрудников только своего отдела. Право руководителя проверяется сервером по идентификатору подразделения. Дополнительные руководители и иерархическое подчинение вне MVP. **Окончательное утверждение карты компетенций выполняет руководитель подразделения.** Ответственный за КК готовит проект и отправляет его на утверждение; без утверждения проект не становится активной картой.

#### 3.8.3. Единый каталог и карты компетенций

1. В системе ведётся **единый справочник** компетенций организации, рассчитанный на сотни и тысячи записей (ориентировочно 500–1000+). У каждой компетенции есть уникальный код, название, категория, описание и критерии оценки.
2. Одна и та же запись справочника может включаться в карты нескольких подразделений. Например, «Установка и настройка PostgreSQL» может входить в карты администраторов серверов и администраторов СУБД; дублировать компетенцию в каталоге для каждого отдела не требуется.
3. Для отдела формируется **карта компетенций (КК)** — набор ссылок на элементы общего справочника. Можно устанавливать целевой уровень для компетенции и фиксировать версию карты.
4. Руководитель определяет потребность отдела в компетенциях. Ответственный за КК формирует проект карты и передаёт руководителю; руководитель **утверждает или возвращает проект на доработку**. Только утверждённая версия получает статус активной и используется для новых назначений. Дата, автор проекта, утвердивший руководитель и версия фиксируются в системе.
5. Компетенции могут быть связаны с материалами базы знаний с помощью общих тегов (`labels` / `competency_labels` / `page_labels`). Тег — способ тематической связи, **не доказательство знаний сотрудника**.
6. Для обязательных проверок список компетенций выбирается из активной карты подразделения. В пределах опубликованного теста компетенции могут быть произвольно сгруппированы в блоки. Общие компетенции оцениваются по единому идентификатору.
7. Сотрудник вправе добавить **дополнительную компетенцию** из общего каталога, даже если она отсутствует в карте его отдела; дополнительные компетенции отмечаются отдельно, не меняют карту отдела и проверяются **только тестом**.
8. Данные о компетенциях сотрудников других отделов в MVP руководителю не предоставляются; поиск взаимозаменяемых работников между подразделениями — будущая функциональность.

**Связь с текущим `schema.sql`:** `competency_categories` — категории; `competencies` — общий справочник; `competency_profiles` и `profile_competencies` — версии карт и их состав; `departments` — подразделения; `employee_competencies` — актуальная оценка сотрудника. Это **описание соответствия**, а не утверждение, что все операции уже обеспечены ограничениями SQL.

#### 3.8.4. Подготовка и контроль качества вопросов

1. Отдельная нейросетевая система (вне состава Conflunce) генерирует вопросы **на основе статей базы знаний** и передаёт результат в структурированном **JSON-файле**.
2. Ответственный за КК импортирует JSON в интерфейс модуля. Приём выполняется в промежуточную область проверки, а не сразу в доступный для назначения банк вопросов.
3. Система проверяет формат JSON, обязательные поля, тип вопроса, количество ответов, корректность ссылки на компетенцию и наличие правильного ответа. Ошибочные записи отображаются с причиной отказа.
4. Ответственный за КК просматривает формулировку, компетенцию, варианты и правильный ответ, при необходимости редактирует и выбирает **«Принять»** или **«Отклонить»**. Отклонённый вопрос не включается в тесты. Принятый вопрос становится доступен при составлении теста.
5. Для каждого вопроса желательно фиксировать статью-источник и её версию, идентификатор импорта, дату, ответственного и решение модерации. Система не принимает утверждения нейросети за достоверные без проверки человеком.
6. В первой версии поддерживаются вопросы с **одним** (`single`) или **несколькими** (`multiple`) правильными вариантами ответа. Условия частичного зачёта при множественном выборе уточняются в разделе 12.

**Предлагаемый минимальный контракт JSON (уточнить по фактическому формату внешней нейросети):** `external_id`, `competency_code`, `source_page_id` (или иной идентификатор статьи), `question`, `type`, `options: [{id, text, is_correct}]`, `explanation` (необязательно). Это проект контракта; формат реально получаемого JSON пока не предоставлен.

#### 3.8.5. Формирование теста и блоков

1. Ответственный за КК создаёт тест с названием, описанием, принадлежностью к подразделению/карте компетенций и статусом `черновик → опубликован → архивирован`.
2. **Тест состоит из одного или нескольких блоков.** Блоки конструируются **произвольно для каждого теста**, имеют название, порядок отображения и содержат **несколько компетенций**. Отдельный общий справочник готовых блоков для MVP не требуется.
3. Ответственный выбирает компетенции из активной карты подразделения и распределяет их по блокам. В одном тесте каждую компетенцию следует учитывать **один раз**, чтобы не допускать двойного начисления; при необходимости повторного упоминания вопрос группировки решается редактором до публикации.
4. В каждой компетенции блока должно быть **не менее двух одобренных вопросов**. Проверка этого требования выполняется до публикации; если хотя бы по одной компетенции вопросов недостаточно, публикация запрещена.
5. В тест включаются только вопросы, прошедшие ручную проверку ответственным за КК. Вопрос привязывается к конкретной компетенции, а компетенция — к блоку.
6. При назначении фиксируется версия опубликованного теста. **При запуске** из этой версии формируется неизменяемый экземпляр прохождения: блоки, допустимые компетенции, вопросы, варианты ответов, правильные ответы и правила оценки. Из него исключаются компетенции, недоступные из-за 30-дневного ограничения, вместе с их вопросами; пустые блоки скрываются только в экземпляре прохождения. Шаблон опубликованного теста и результаты прежних прохождений не изменяются.
7. Внутренний показатель `passing_percent` допускается для справки, но не заменяет оценку **отдельно по каждой компетенции**. Итоговый балл блока не служит оценкой его компетенций.
8. Для **самостоятельного тестирования** сотрудника ответственный за КК публикует готовые тесты, доступные для выбора по компетенции. При запуске система должна проверить, что выбранная компетенция входит в состав готового теста и может быть оценена по его вопросам. Автоматическая генерация нового теста сотрудником не допускается.

#### 3.8.6. Назначение проверки руководителем

1. Руководитель выбирает одного из своих подчинённых и опубликованный тест **либо** назначает собеседование по выбранным компетенциям.
2. При назначении указываются набор проверяемых компетенций, тип проверки, дата назначения и **крайний срок**; для собеседования дополнительно — собеседующий и согласованное время/дата проведения.
3. Сотрудник видит назначение в «Моих компетенциях»: тип, тему, проверяемые компетенции, срок и статус. В текущей версии предусмотрено уведомление **в интерфейсе**, без обязательных email-рассылок.
4. Статусы назначения (предлагаемые): `назначено`, `в процессе`, `завершено`, `просрочено`, `отменено`. Просроченное тестирование нельзя начать без нового решения руководителя; поведение уже начатого теста при наступлении срока уточняется.
5. Назначение нового подтверждающего теста для уровня 3 — **отдельная проверка/назначение**, а не дополнительная попытка по исходному назначению. Повторная проверка **той же компетенции** возможна не ранее чем через **30 календарных дней** после завершения предыдущей проверки этой компетенции; правило распространяется и на подтверждение уровня 3. Если назначенный тест включает пока недоступные компетенции, их исключают при запуске, а остальные проверяют без изменения опубликованного теста.
6. Для самостоятельной проверки дополнительной компетенции назначение создаётся **автоматически от имени системы при запуске опубликованного теста сотрудником**, без согласования руководителя; у такого назначения фиксируется тип `self_assigned` и одна попытка. Установка дедлайна руководителем к этому случаю не применяется.

#### 3.8.7. Прохождение теста сотрудником

1. Сотрудник открывает назначенный тест, проверяет информацию о сроке и запускает прохождение.
2. **Ровно одна попытка на одно назначение.** Повторный запуск после финальной отправки и создание второй попытки для того же назначения запрещены на уровне базы данных и бизнес-логики.
3. Ответы сохраняются по конкретным вопросам. Для предотвращения случайной потери данных допускается сохранение текущего состояния **в пределах той же попытки**; пересдачей это не считается.
4. После отправки ответы блокируются для изменения, система подсчитывает результат **отдельно по каждой компетенции**; общий процент правильных ответов можно показывать дополнительно.
5. Сотрудник получает сводку результатов и актуальные уровни компетенций. Правильные ответы и их раскрытие после завершения — отдельное решение (раздел 12), чтобы не облегчить повторные/подтверждающие проверки.
6. Результаты, время начала/завершения и использованный вариант теста сохраняются для аудита. Сотрудник не может произвольно изменять оценки.
7. **Непосредственно перед запуском** система проверяет 30-дневный интервал отдельно по каждой компетенции относительно последней завершённой проверки. Компетенции, для которых срок ещё не истёк, **исключаются из экземпляра прохождения** вместе с вопросами; остальные компетенции доступны. Исключённые компетенции не получают новую оценку, не отмечаются как проваленные и не расходуют попытку по соответствующей компетенции. Если после исключения не осталось ни одной проверяемой компетенции, запуск не разрешается и попытка не создаётся. Сотрудник видит, что исключено, по какой причине и когда проверка вновь станет доступна. Проверка выполняется сервером для самоназначения и назначения руководителем; прохождение через другой тест ограничение не обходит.

#### 3.8.8. Собеседование

1. Руководитель назначает собеседование по одной или нескольким компетенциям и определяет собеседующего.
2. Сотрудник видит назначенную дату, время, перечень компетенций и статус.
3. После беседы собеседующий выставляет **отдельный уровень 0, 1, 2 или 3 по каждой проверенной компетенции**, при необходимости добавляет комментарий и фиксирует дату проведения.
4. Оценка собеседования является экспертной; в отличие от автоматического теста она основана на выводе собеседующего по критериям компетенции.
5. Уровень 3 при собеседовании допустим при явном подтверждении владения компетенцией, с фиксацией того, кто подтвердил результат и на каком основании.

#### 3.8.9. Правила оценки и подтверждения компетенций

**Единая шкала для модуля — от 0 до 3 включительно.** Результат фиксируется *по каждой компетенции*, а не только по тесту в целом.

| Уровень | Смысл | Автоматическое тестирование | Собеседование |
|---|---|---|---|
| **0 — не подтверждено** | Нет правильных ответов / знания не выявлены | Нет правильных ответов по компетенции, включая все оставленные без ответа | Собеседующий не выявил достаточных знаний |
| **1 — базовые знания** | Есть отдельные верные ответы, но знания неполные | Есть хотя бы один правильный ответ, но не все вопросы компетенции выполнены верно | По экспертной оценке выявлены частичные знания |
| **2 — знания подтверждены первичной проверкой** | Полный результат первичной проверки | **Все** вопросы данной компетенции выполнены верно (не менее двух) | Собеседующий подтвердил уверенное владение, но не присвоил высший уровень |
| **3 — дополнительно подтверждено** | Знания подтверждены отдельной контрольной проверкой | **Не присваивается по одной первичной попытке**. Требуется отдельное подтверждающее тестирование или собеседование | Собеседующий может присвоить 3 при наличии подтверждающей проверки и зафиксированного основания |

**Правила вычисления:** для теста считать вопрос верным, только если выбранный набор вариантов полностью соответствует ключу; по каждой компетенции рассчитывать `correct / total`, где вопросы без ответа считаются неверными. `0` — `correct = 0`; `1` — `0 < correct < total`; `2` — `correct = total`. Первичная проверка не выставляет `3` автоматически. Для подтверждения `3` **необходимо** наличие ранее полученного уровня `2` и успешная отдельная подтверждающая проверка **по той же компетенции** (полностью правильный подтверждающий тест **только с новыми вопросами, не использованными при первичной проверке этой компетенции**, или положительное экспертное собеседование для основной компетенции); для дополнительных компетенций подтверждение возможно **только повторным тестом**. Между завершёнными проверками одной компетенции выдерживается минимум 30 календарных дней; при изменении компетенции между проверками подтверждение не переносится на другую компетенцию. Если у сотрудника **вообще не было проверки**, в профиле показывается «Не оценено», **не 0**.

**Новые вопросы для уровня 3:** для подтверждающего теста система проверяет непересечение идентификаторов (и зафиксированных версий) вопросов с первичным тестом по этой компетенции. Необходимо не менее двух новых одобренных вопросов. При недостаточном банке новых вопросов подтверждающий тест по компетенции недоступен; ответственный за КК должен пополнить банк. Редактирование старого вопроса не должно автоматически превращать его в новый вопрос для подтверждения.

**Важно для проектирования:** «одна попытка» относится к одному назначению. Повторное *подтверждающее тестирование* — отдельное назначение с одной собственной попыткой. **В профиле сохраняется максимальный достигнутый уровень** по каждой компетенции; менее успешная повторная проверка не снижает этот уровень. При этом отдельным событием сохраняется **результат последней проверки**, дата и источник, чтобы история не терялась. Результаты неоценивавшихся компетенций — «Не оценено», а не 0.

#### 3.8.10. Личный кабинет и сводка подразделения

**Сотрудник («Мои компетенции»):**
- список компетенций, входящих в карту его подразделения, с текущим уровнем (`Не оценено`, 0, 1, 2, 3), датой и источником последней оценки;
- список назначенных тестов и собеседований с крайними сроками и статусами;
- результаты завершённых проверок, распределённые по компетенциям, и история оценок;
- различие между «не оценено» и «оценено на 0»;
- отдельная вкладка «Дополнительные компетенции»: поиск по общему каталогу, добавление компетенции, запуск готового опубликованного теста без согласования, результаты и дата следующей доступной проверки (30 дней);
- отображение максимального уровня и результата последней проверки без понижения максимального уровня.

**Руководитель («Компетенции подразделения»):**
- перечень подчинённых и их компетенций с текущими уровнями и датами оценок;
- сводка по компетенциям отдела (сколько сотрудников имеют уровни 0, 1, 2, 3 и сколько ещё не оценены);
- назначенные, завершённые и просроченные проверки;
- назначение новых тестов/собеседований и просмотр результатов в пределах своих полномочий;
- видимость дополнительных компетенций своих сотрудников в профилях/сводке собственного отдела (не в качестве обязательного состава карты).

Для задачи поиска взаимозаменяемости предусмотрен **потенциал дальнейшего развития**: сравнение компетенций смежных отделов и поиск сотрудников с нужными навыками. В MVP **только сводка своего отдела**; просмотр компетенций сотрудников других подразделений и межотдельский поиск исключены.

#### 3.8.11. Требования к данным и согласование с `schema.sql`

| `test_assignments`, `test_attempts`, `attempt_answers`, `attempt_selected_options` | Назначения и попытки | Ограничение **одной** попытки на назначение (`UNIQUE (assignment_id)`); тип назначения (`manager_assigned`/`self_assigned`), срок, статусы, необратимая отправка; результаты по компетенциям, серверная проверка интервала 30 дней, фиксация **исключённых компетенций и причин** на момент запуска, без оценивания исключённых |
| `interviews`, `interview_ratings` | Собеседования и экспертные оценки | Привязать собеседование к назначению руководителя, дедлайну и списку выбранных компетенций |

| **Новая связь сотрудник ↔ дополнительная компетенция** | Самостоятельно выбранные навыки вне карты отдела | Хранить автора выбора, время добавления, вид компетенции (`additional`); не дублировать записи каталога |
| `competency_assessments`, `competency_scores`, `competency_scales` | Альтернативная групповая модель оценок | Утвердить их назначение относительно событий и актуальных оценок, чтобы не создавать конфликтующих источников истины |

Текущий `schema.sql` **не изменён в рамках данного ТЗ**. В нём уровни компетенций сейчас допускают значения `0..10`, а `test_attempts` разрешает несколько попыток через `attempt_no`; это не соответствует установленным выше новым правилам и должно быть исправлено отдельной миграцией/редакцией схемы. Также в схеме нет самостоятельного жизненного цикла AI-импорта и модерации вопросов.

| KK-25 | Ответственный за КК предлагает новую карту отдела | Карта остаётся проектом, пока руководитель отдела не утвердит её |
| KK-26 | Подтверждающий тест содержит вопросы из первичного теста | Вопросы не допускаются в подтверждающую проверку; при нехватке новых вопросов подтверждение не запускается |
| KK-27 | У теста все компетенции ещё находятся под 30-дневным ограничением | Запуск запрещён без создания попытки; указаны даты доступности |
| KK-28 | После фильтрации в блоке не осталось компетенций | Пустой блок скрыт в экземпляре прохождения, но сохранён в опубликованном шаблоне |

### 5.3. Потоковая передача медиа

- Эндпоинт `/media/stream/<media_id>` получает заголовок `Range`.  
- Backend использует `psycopg2` `cursor.fetchone()` с `SUBSTRING(data FROM offset FOR length)` чтобы отдавать куски без полной загрузки в память.  
- Ответ `206 Partial Content` + `Content-Range` header.

### 5.4. Подсистема компетенций (расширение архитектуры)

Подсистема использует существующие `users`, `departments`, RBAC, базу знаний и PostgreSQL. Дополнительно выделяются логические сервисы: **каталог и карты компетенций**, **импорт/модерация вопросов**, **конструктор тестов**, **назначения и проведение проверок**, **расчёт оценок 0–3**, **отчёты по сотрудникам и отделам**. Эти блоки могут быть реализованы внутри одного Python-приложения и не требуют выделения микросервисов.

Внешняя нейросеть **не входит** в состав разрабатываемого приложения: Conflunce принимает её JSON-файл и проводит проверку человеком. Теги связывают компетенции с тематическими страницами вики. Перед сохранением итогов проверок сервер проверяет полномочия, однократность попытки и доступность назначенных компетенций.

**Поток данных:** статья базы знаний → внешний AI-генератор → JSON → импорт → модерация → банк вопросов → тест по компетенциям → назначение руководителем → однократная попытка сотрудника → оценки по компетенциям → личный кабинет и сводка руководителя. Вторая ветка: карта компетенций → назначение собеседования → экспертные оценки → общий журнал результатов.

## 12. Зафиксированные решения и остающиеся вопросы

### 12.1. Подтверждённые требования для MVP

1. **Подчинённость:** один руководитель на отдел, сотрудник относится к отделу; руководитель видит только свой отдел.
2. **Структура теста:** тест содержит создаваемые для него блоки; каждый блок содержит несколько компетенций; каждая компетенция оценивается отдельно.
3. **Покрытие вопросов:** минимум **два** принятых вопроса по каждой компетенции в тесте; тест с меньшим количеством не публикуется.
4. **Дополнительные компетенции:** сотрудник сам добавляет компетенции из общего каталога, может без согласования начать готовый опубликованный тест; **собеседование не используется**.
5. **Повторная проверка:** не чаще одного раза в **30 календарных дней по конкретной компетенции** (включая другой тест или подтверждающую проверку).
6. **Попытки:** строго одна попытка на одно назначение/самостоятельный запуск.
7. **Оценки:** 0 — ни одного правильного; 1 — часть правильных; 2 — все правильные (при ≥2 вопросах); 3 — ранее 2 и отдельная успешная подтверждающая проверка. Дополнительную компетенцию подтверждают на 3 только тестом.
8. **Сохранение результата:** отображается **высший достигнутый уровень**; последнее прохождение и все оценки хранятся в истории.
9. **Межотдельский доступ:** отсутствует в MVP; межотдельский поиск компетенций отложен.
10. **Утверждение карт:** проект составляет ответственный за КК, окончательно утверждает руководитель отдела.
11. **Подтверждение уровня 3 тестом:** только новые вопросы по сравнению с первичным тестированием конкретной компетенции; минимум два новых вопроса.
12. **30-дневное ограничение в составном тесте:** исключать только временно недоступные компетенции; остальные оставлять. Если не осталось ни одной, тест не запускается.

### 12.2. Открытые вопросы (не блокируют фиксацию уже утверждённых правил)

1. Может ли один ответственный за КК обслуживать несколько отделов, кто назначает его полномочия?
2. Кто может быть собеседующим и вправе подтверждать уровень 3: назначенный эксперт, ответственный за КК, руководитель?
3. Как поступать с незавершённой единственной попыткой при дедлайне и техническом сбое?
4. Какой фактический JSON выдаёт нейросеть? Требуется образец для закрепления формата импорта.
5. Сколько дополнительных компетенций можно одновременно добавить в профиль? Нужны ли ограничения количества активных проверок?
6. Какие данные показывать после сдачи: уровни/ошибки/полные правильные ответы?
7. Для самостоятельной проверки дополнительной компетенции: как выбирать готовый тест, если он содержит несколько компетенций (оставлять все доступные или только выбранную сотрудником)?
8. Нужна ли массовая выдача одного теста нескольким сотрудникам?
9. Как распределить ответственность между существующими таблицами `competency_assessments`, `competency_scores` и `competency_assessment_events`, чтобы исключить противоречащие друг другу оценки?
