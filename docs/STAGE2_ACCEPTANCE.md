# Stage2 — ручная приёмка блоков и версий

Этот portable-пакет содержит Stage2. Адрес стенда и пароли задаются владельцем отдельно; инфраструктура и секреты исходного dev сюда не включены. Следующий этап — только после подтверждения пользователя.

## Действия

1. **Компетенции → Ответственный за КК → Новый тест**: ввести название/описание, произвольные названия двух блоков, выбрать по две компетенции активной утверждённой карты и по два утверждённых вопроса. **«Добавить блок»**, **«Блок вверх/вниз»**, **«Компетенция вверх/вниз»**, **«Вопрос вверх/вниз»** задают структуру и порядок. **«Создать тест» → «Опубликовать»** создаёт v1.
2. **Руководитель → Назначить тест**: выбирать только новых проверочных сотрудников и будущий срок. Создать два назначения v1; одно начать сотрудником, другое оставить неначатым.
3. КК: **«Создать новую версию»** — редактор остаётся открытым. Изменить названия/порядок блоков, перенести компетенции, выбрать другие утверждённые вопросы; при необходимости создать и одобрить новый вопрос, не править старый банк. **«Сохранить черновик» → «Опубликовать»** создаёт v2. Во время черновика руководителю всё ещё доступна v1.
4. Руководитель: последняя версия назначает v2, явный выбор **«Версия 1»** — v1. **«Просмотреть опубликованные версии» → «Открыть версию 1/2»** показывает неизменяемое содержимое без ключей.
5. Старые начатая/неначатая попытки должны использовать v1. Новый сотрудник на v2 видит два именованных блока; **«Отправить ответы»** показывает версию и результаты по компетенциям. Пустые ответы неверные. Сохранить один свежий аккаунт с assigned v2 **без старта** для ручной приёмки.
6. Отдельным новым smoke сначала пройти небольшой тест с компетенциями первого блока, затем полный: исключённый целиком блок скрыт, нулевых результатов исключённым компетенциям нет. Отдельный новый smoke-тест архивировать: новые назначения запрещены, старое можно закончить. Основной демонстрационный тест не архивировать.

## Ограничения

- Название теста нельзя изменить после первой публикации; названия блоков меняются в новой версии.
- 1–10 блоков, минимум 2 компетенции в блоке, максимум 20 в тесте, без повторения компетенций.
- Явный выбор 0–50 вопросов в черновике, 2–50 утверждённых активных вопросов для публикации. В демонстрации по два.
- Старые назначения/попытки закреплены за версией; новая публикация их не меняет.
- После завершения — 30-дневный cooldown. Не сбрасывать старые результаты ради проверки.
- Ответы сохраняются при отправке, не при выборе. До отправки не закрывать вкладку. Перед обновлением существующих вкладок сохранить несохранённый текст.

## Выполненная проверка исходного dev

Реальный Chromium: UI create/publish v1/v2, изменение структуры/вопросов, pending/in-progress v1 после v2, explicit/default assignments, прохождение v2 и версия в результатах, частичные пустые ответы, исключённый блок, отдельный архив, desktop/mobile ручного аккаунта без старта. Созданы только новые smoke-сущности: 7 пользователей, 3 теста, 4 публикации, 8 назначений, 7 завершённых попыток, 44 ответа, 22 результата; один ручной сотрудник оставлен assigned v2.

В успешных сценариях 0 JS/console errors, request failures и неожиданных HTTP errors; отрицательные API — 403×7 и 409×1. Старые строки сохранены: 485/485, включая audit, исключая auth sessions/login limits. Миграции/seed/reset не выполнялись. Runtime-исправлений приложения не потребовалось; две ошибки браузерного harness исправлены и сохранены в журнале исходного dev.

Python: 153 discovered, 145 passed, 8 opt-in skipped; frontend: 57/57; offline seed-helper unit: 12/12. Ранее изолированные PG: 7 DB + 3 safety = 10/10, concurrency 1 test / 6 subtests. Гонки, legacy и сохранение прежнего max-level проверялись в изолированной БД, не путём изменения старых данных dev.

Это результат проверки исходного dev, **не утверждение о развёртывании данного пакета на другом сервере**. На новом окружении повторить приёмку с собственными безопасными fixtures и резервной копией.
