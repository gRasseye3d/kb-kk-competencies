# Conflunce — изменения структуры БД для ТЗ v4

Файл `schema_conflunce_v4.sql` предназначен для **создания новой БД PostgreSQL 15+**. Это не `ALTER`-миграция существующей схемы. Исходный `schema.sql` не изменён.

## Основные изменения

- Отдел → один руководитель через `departments.manager_id`; назначение ответственных за КК — `department_kk_responsibles`.
- Карта компетенций: статусы подготовки, представления на утверждение и утверждения руководителем (`competency_profiles`); одна активная карта на отдел (частичный уникальный индекс).
- Единый каталог компетенций, шкала 0–3; дополнительные навыки — `employee_additional_competencies`.
- JSON от внешней нейросети: `question_imports`, `question_import_items`; проверка ответственным, исходные статьи, версии вопросов (`question_revisions`).
- Блоки тестов — `test_blocks`; компетенции в блоке — `test_block_competencies`; вопросы связаны с компетенциями через внешние ключи.
- Версии опубликованных тестов — `test_versions` с JSONB снимком. Каждое назначение фиксирует версию.
- Тестовые назначения: `manager_assigned`/`self_assigned`, первичная/подтверждающая проверка, статусы и дедлайн.
- `UNIQUE(test_attempts.assignment_id)` гарантирует максимум одну попытку на назначение.
- `attempt_competencies` фиксирует допущенные/исключённые компетенции и дату доступности; `attempt_questions` фиксирует реально показанные вопросы и версии; `test_competency_results` фиксирует результаты **по компетенциям**.
- `assessment_cooldowns` хранит дату следующей проверки; история — `competency_assessment_events`, максимальный и последний уровни — `employee_competencies`.
- Собеседования содержат назначающего, срок, цель и список компетенций (`interview_competencies`).
- Добавлены отсутствующие в базе знаний элементы ТЗ: `templates`, `page_approvals`, `audit_log`, хранение медиа кусками в PostgreSQL (`attachment_chunks.encrypted_data BYTEA`) вместо внешнего `storage_key`.

## Инварианты, которые ещё требует обеспечить backend

SQL ограничивает значения и связи, но **не заменяет бизнес-логику**:

1. Только руководитель своего отдела утверждает карту и назначает проверки подчинённым; ответственный за КК формирует карту и проверяет вопросы.
2. До публикации теста: все вопросы одобрены, у каждого блока несколько компетенций и по каждой компетенции не менее двух вопросов. Опубликованная версия неизменна.
3. При запуске теста в транзакции проверяются 30 дней по **каждой** компетенции, доступные включаются в экземпляр, недоступные исключаются; если включённых нет, попытка не создаётся. Требуется сериализация конкурентных запусков по паре (сотрудник, компетенция) — например, блокировка строки/адвайзори-лок.
4. Для уровня 3: прежде было подтверждено 2; проверка отдельная; минимум два вопроса, ранее не использованных в первичной проверке по этой компетенции; для дополнительных компетенций запрещено собеседование.
5. На завершении пересчитывается результат каждого вопроса по замороженному ключу, создаётся событие, обновляется максимум `GREATEST(старый, новый)` и последняя оценка; обновляется `assessment_cooldowns`. Всё в одной транзакции.
6. Снимок (`frozen_structure`, `frozen_question`) хранит ответы, но сервер не должен раскрывать правильные варианты пользователю до разрешённого момента.
7. Доступ к результатам других подразделений запрещается в сервисном слое. После финальной отправки ответы и снимки не должны допускать изменений. Ссылки на страницы, версии и компетенции нужно дополнительно проверять на согласованность.
8. Для чанкового `pgp_sym_encrypt` ключи остаются вне БД, шифруется каждый чанк независимо; нужна реализация Range, ротации ключей и проверки непрерывности чанков.

## Неурегулированные вопросы из ТЗ v4

- Роли собеседующего и критерии его назначения.
- Формат реального JSON нейросети.
- Для самостоятельно выбранной компетенции: запускать весь готовый многокомпетентностный тест или только выбранную компетенцию.
- Правила раскрытия правильных ответов и ограничения активных самостоятельных назначений.
- Обработка просроченного теста, который уже начат.

## Степень проверки

Выполнена **статическая** сверка уникальности таблиц, наличия целевых таблиц внешних ключей, базовых ограничений и наличия `BEGIN/COMMIT`. В доступной среде отсутствуют `psql` и запущенный PostgreSQL; полноценный запуск DDL в сервере, проверка всех FK и интеграционные тесты пока не проводились. Для приёмки нужно запустить SQL в пустой тестовой базе PostgreSQL 15+ и прогнать сценарии ТЗ KK-01–KK-28.
